# 👤 4.2 Linux User & Group Management

Welcome to **Linux User & Group Management**.

Linux is a **multi-user operating system**, which means multiple users can work on the same Linux system while having different permissions and access levels.

In real companies, Linux servers are usually accessed by many people:

```text
Developers
    ↓
Application Support
    ↓
DevOps Engineers
    ↓
System Administrators
    ↓
Database Administrators
```

Each person should not have unrestricted access to everything.

Linux provides **users, groups, permissions, and `sudo`** to control who can access what.

# 1. What is a Linux User?

A **Linux user** is an account that can interact with the Linux system.

A user account identifies:

- Who is accessing the system
- What permissions they have
- Which groups they belong to
- What their home directory is
- Which shell they use
- What processes they can run

Example:

```text
sahil
```

could be a Linux user.

---

# 2. Why Do We Need Users?

Imagine a company has one production Linux server.

There are:

```text
Developer
Application Support Engineer
DevOps Engineer
Database Administrator
System Administrator
```

If everyone uses the same `root` account, there is a major security problem.

Nobody can easily determine:

> Who performed which action?

And everyone would have extremely high privileges.

Instead, Linux allows separate accounts:

```text
developer1
support1
devops1
dba1
admin1
```

Each account can have different permissions.

---

# 3. Real-Life Example

Think about an office building.

There are different employees:

```text
Employee A
Employee B
Manager
Security Officer
Administrator
```

They don't all have access to every room.

For example:

```text
Employee
   ↓
Office Area

Manager
   ↓
Office + Manager Room

Administrator
   ↓
Most Areas
```

Linux works similarly.

```text
Linux Server
     │
     ├── User A
     ├── User B
     ├── User C
     └── User D
```

Each user can have different access.

| User | Role |
|---|---|
| `support01` | Application Support |
| `developer01` | Developer |
| `devops01` | DevOps |
| `dba01` | Database |
| `admin01` | System Administrator |

The actual usernames depend on company policies.

---

# 5. What is a Linux Group?

A **group** is a collection of users.

Instead of assigning permissions individually to every user, we can assign permissions to a group.

Example:

```text
Application Support Group
        │
        ├── support01
        ├── support02
        └── support03
```

Now permissions can be assigned to:

```text
support-group
```

instead of separately configuring:

```text
support01
support02
support03
```

---

# 6. Why Do We Need Groups?

Suppose a company has:

```text
20 Application Support Engineers
```

They all need access to:

```text
/opt/application/logs
```

Without groups, you might manage permissions user by user.

That becomes difficult.

Instead:

```text
support01 ─┐
support02 ─┤
support03 ─┤
support04 ─┤
support05 ─┘
      ↓
support-group
      ↓
/opt/application/logs
```

Now permissions can be managed at the group level.

---

# 7. Users vs Groups

| User | Group |
|---|---|
| Represents an individual account | Represents a collection |
| Can log into the system | Usually used for access management |
| Has UID | Has GID |
| Has home directory | Normally doesn't have a personal home directory |
| Can belong to multiple groups | Contains multiple users |

Example:

```text
User:
sahil

Groups:
support
developers
docker
```

---

# 8. Root User

Linux has a special user called:

```text
root
```

Root is the **superuser**.

Root has very high privileges.

Root can generally:

- Create users
- Delete users
- Create groups
- Modify permissions
- Install software
- Stop services
- Start services
- Change system configuration
- Access protected files

Example:

```text
root@server01:~#
```

The `#` commonly indicates a root shell.

---

# 9. Normal User

A normal user has limited privileges.

Example:

```text
sahil@server01:~$
```

A normal user may be able to:

```text
Read their files
Create files in their home directory
Run applications
Execute permitted commands
```

But may not be able to:

```text
Modify system files
Install system packages
Restart protected services
Create other users
```

unless additional privileges are granted.

---

# 10. System Users

Linux also uses **system/service accounts**.

These accounts are usually created for applications or services.

Examples may include:

```text
www-data
nginx
mysql
postgres
redis
```

The exact accounts depend on the software installed.

Example:

```text
Nginx
   ↓
nginx user

Database
   ↓
postgres user
```

Why?

Running applications under dedicated users limits what the application can access.

This is an important security principle:

> Give an application only the permissions it actually needs.

# 11. UID

UID means:

> **User ID**

Every Linux user has a numeric UID.

Example:

```bash
id sahil
```

Possible output:

```text
uid=1000(sahil) gid=1000(sahil) groups=1000(sahil)
```

Here:

```text
1000
```

is the UID.

Linux internally identifies users using numeric IDs.

---

# 12. GID

GID means:

> **Group ID**

Every Linux group has a numeric GID.

Example:

```bash
id sahil
```

Possible output:

```text
uid=1000(sahil)
gid=1000(sahil)
```

Here:

```text
1000
```

is the primary group ID.

# 13. /etc/passwd

One important Linux file is:

```text
/etc/passwd
```

It contains information about user accounts.

View it with:

```bash
cat /etc/passwd
```

You may see:

```text
root:x:0:0:root:/root:/bin/bash
```

A typical entry follows a structure similar to:

```text
username:x:UID:GID:comment:home:shell
```

Example:

```text
sahil:x:1000:1000:Sahil:/home/sahil:/bin/bash
```

Meaning:

```text
Username  → sahil
UID       → 1000
GID       → 1000
Home      → /home/sahil
Shell     → /bin/bash
```

---

# 14. /etc/shadow

Another important file is:

```text
/etc/shadow
```

It contains sensitive authentication information such as password hashes and account aging information.

View it carefully:

```bash
sudo cat /etc/shadow
```

Normally, regular users cannot read this file.

### Important

Do not modify `/etc/shadow` manually.

Use commands such as:

```bash
passwd
```

to manage passwords.

---

# 15. /etc/group

Group information is stored in:

```text
/etc/group
```

View it using:

```bash
cat /etc/group
```

Example:

```text
support:x:2001:sahil,rahul
```

This indicates that:

```text
Group:
support

Members:
sahil
rahul
```

# 21. Set a Password

After creating a user, set a password:

```bash
sudo passwd rahul
```

The system will ask you to enter the password.

Example:

```text
New password:

passwd: password updated successfully
```

# 22. Modify a User

The command used to modify users is:

```bash
usermod
```

General structure:

```bash
sudo usermod [options] username
```

Example:

```bash
sudo usermod -c "Application Support Engineer" rahul
```

The `-c` option changes the comment/full-name field.

---

# 23. Change User's Home Directory

You can change a user's home directory using:

```bash
sudo usermod -d /home/newhome rahul
```

To move the existing home directory as well:

```bash
sudo usermod -d /home/newhome -m rahul
```

The `-m` moves the contents to the new location.

---

# 24. Change User's Shell

You can change the user's login shell.

Example:

```bash
sudo usermod -s /bin/bash rahul
```

Check:

```bash
grep '^rahul:' /etc/passwd
```

# 25. Lock a User

If an employee leaves the company or an account must temporarily be disabled, you can lock the account.

```bash
sudo usermod -L rahul
```

Another common command:

```bash
sudo passwd -l rahul
```

The account remains present but password-based login is disabled.

# 26. Unlock a User

To unlock:

```bash
sudo usermod -U rahul
```

or:

```bash

```

# 27. Expire a User

Account expiration can be managed using:

```bash

```

```bash

```

Example information may include:

```text

Account expires
```

# 28. Delete a User

To delete a user:

```bash
sudo userdel rahul
```

This removes the user account.

However, depending on how the account was created and the command used, the home directory may remain.

---

# 29. Delete User and Home Directory

To remove the user and their home directory:

```bash
sudo userdel -r rahul
```

The `-r` option removes associated home/mail files where applicable.

### ⚠️ Be Careful

Do not run this command on a production user without confirming:

- Who owns the account
- Whether it is still required
- Whether files need to be backed up
- Whether the user owns application files
- Whether the account is used by automation

# 32. Add User to a Group

This is one of the most important commands.

Example:

```bash
sudo usermod -aG support rahul
```

Meaning:

```text
usermod
   ↓
Modify user

-a
   ↓
Append

-G
   ↓
Secondary group

support
   ↓
Group name

rahul
   ↓
User
```

### Important

Use:

```bash
-aG
```

instead of only:

```bash
-G
```

because `-a` means **append** the group without removing the user's existing supplementary groups.

# 33. Primary and Secondary Groups

A user can belong to:

- One primary group
- Multiple secondary/supplementary groups

Example:

```text
User: rahul

Primary Group:
rahul

Secondary Groups:
support
docker
developers
```

Diagram:

```text
                 rahul
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
       rahul     support   docker
       Primary   Secondary Secondary
```

---

# 34. Change Primary Group

Use:

```bash
sudo usermod -g support rahul
```

Here:

```text
-g
```

sets the primary group.

Check:

```bash
id rahul
```

---

# 35. Remove User from a Group

On systems with GNU `usermod`, you can replace the supplementary group list with the desired groups.

For example, if `rahul` should belong to `support` but no longer `developers`:

```bash
sudo usermod -G support rahul
```

### ⚠️ Important

Using `-G` without `-a` **replaces** the supplementary group list.

This can unintentionally remove other group memberships.

A safer approach is to explicitly specify all desired supplementary groups:

```bash
sudo usermod -G support,docker rahul
```

Another commonly available command is:

```bash
sudo gpasswd -d rahul developers
```

This removes `rahul` from the `developers` group.

Always verify:

```bash
id rahul
```

# 39. sudo

`sudo` means:

> **Superuser Do**

It allows an authorized user to execute a command with elevated privileges.

Example:

```bash
sudo systemctl restart nginx
```

Instead of switching completely to root, the user performs only the required administrative command.

---

# 40. sudo Group

Many Linux distributions use a special administrative group.

On Debian/Ubuntu systems, this is commonly:

```text
sudo
```

On Red Hat-family systems, administrative access is commonly associated with:

```text
wheel
```

Example:

```bash
sudo usermod -aG sudo rahul
```

On a system using the `wheel` group:

```bash
sudo usermod -aG wheel rahul
```

After the group membership is applied, the user may need to log out and log back in before the new group membership is reflected in a new session.

Verify:

```bash
groups rahul
```

# 41. User Switching

Linux provides commands for switching users.

---

## `su`

Example:

```bash
su - rahul
```

This starts a login shell as `rahul`.

Return:

```bash
exit
```

---

## `sudo -u`

You can execute a specific command as another user:

```bash
sudo -u rahul whoami
```

Output:

```text
rahul
```

This is useful when testing whether a particular service account can access something.

---

# 42. su vs sudo

| `su` | `sudo` |
|---|---|
| Switches to another user | Executes a command with another user's privileges |
| Can start a full shell | Usually runs one command |
| Often requires target user's password | Usually uses caller's authorized credentials |
| Useful for user switching | Better for controlled administrative access |

### Example

Switch user:

```bash
su - rahul
```

Run one command as user:

```bash
sudo -u rahul whoami
```

---

# 43. User Management Best Practices

In production environments, follow these principles.

## 1. Don't share accounts

Bad:

```text
support
```

used by 10 people.

Better:

```text
sahil
rahul
amit
neha
```

Each person has their own account.

---

## 2. Avoid direct root login

Use individual accounts with controlled `sudo` access.

---

## 3. Give minimum required access

This is called:

> **Principle of Least Privilege**

If a support engineer only needs to restart one application, they should not automatically receive unrestricted root access.

---

## 4. Remove inactive accounts

When an employee leaves:

```text
Disable account
      ↓
Remove access
      ↓
Review files
      ↓
Review SSH keys
      ↓
Review group membership
```

---

## 5. Use groups for access management

Instead of managing:

```text
20 users
```

individually, create:

```text
support-group
```

and manage access through the group.

---

## 6. Never share passwords

Every employee should use their own credentials.

# 47. Troubleshooting

User and group management often causes problems.

---

## Problem 1 — User already exists

You run:

```bash
sudo useradd rahul
```

and get an error indicating the user already exists.

Check:

```bash
id rahul
```

You can also use:

```bash
getent passwd rahul
```

---

## Problem 2 — Group already exists

Check:

```bash
getent group app-support
```

---

## Problem 3 — User not showing new group

After:

```bash
sudo usermod -aG app-support rahul
```

the user's current session may not immediately reflect the new membership.

Check:

```bash
id rahul
```

For a new login session, log out and log back in.

---

## Problem 4 — Permission denied

Example:

```text
Permission denied
```

Check:

```bash
whoami
```

Then:

```bash
id
```

Then inspect the target file/directory:

```bash
ls -ld /path/to/directory
```

Permission problems will be studied in detail in:

**4.3 Permissions & Ownership**

---

## Problem 5 — User cannot use sudo

Check group membership:

```bash
groups rahul
```

Check whether the account has appropriate administrative authorization.

For example:

```bash
sudo -l -U rahul
```

This can show what `sudo` permissions are available, subject to system configuration.

# 🏭 Production Mindset

In a real production environment, **never run user-management commands blindly**.

Before modifying an account, ask:

```text
Who is this user?
       ↓
Why does the account exist?
       ↓
Which groups does the user belong to?
       ↓
What files/processes are associated with it?
       ↓
Will the change affect an application?
       ↓
Is there an approved ticket/change?
       ↓
Then make the change
       ↓
Verify the result
```

This is especially important in Application Support.

# ⭐ Final Note

Remember:

> **Users identify who you are. Groups organize users. Permissions decide what they can do.**

The relationship is:

```text
                 Linux Server
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
       Users                    Groups
          │                       │
          └───────────┬───────────┘
                      ↓
                 Permissions
                      ↓
             Files / Directories
                      ↓
                Applications
```

This is one of the most important foundations for Linux administration, Application Support, DevOps, and Cloud.
