# 🔐 4.3 Linux Permissions & Ownership

Linux is a **multi-user operating system**.

We already learned:

```text
Users
   ↓
Groups
```

But knowing who a user is is not enough.

Linux also needs to answer:

> **What is this user allowed to do?**

This is where **ownership and permissions** come into the picture.

For example, imagine a production server containing:

```text
/opt/myapp/
├── config/
├── logs/
├── scripts/
└── application/
```

Should every user be able to:

- Read configuration files?
- Modify configuration files?
- Delete logs?
- Execute deployment scripts?
- Access application data?

Obviously, no.

Linux permissions help control this access.

# 1. What Are Linux Permissions?

Linux permissions determine what users can do with files and directories.

The three basic permissions are:

```text
r → Read
w → Write
x → Execute
```

For example:

```text
-rwxr-xr--
```

This tells Linux:

```text
Who can read?
Who can write?
Who can execute?
```

---

# 2. Why Permissions Are Important

Imagine a production server.

There is a configuration file:

```text
/opt/myapp/config/application.conf
```

This file may contain important application configuration.

If every user can modify it:

```text
User A ──┐
User B ──┤
User C ──┼──> Modify Configuration
User D ──┤
User E ──┘
```

Someone could accidentally break the application.

A better setup might be:

```text
Application Owner
       ↓
Read + Write

Application Support
       ↓
Read

Others
       ↓
No Access
```

This is why Linux permissions are critical.

Think about a company office.

There might be:

```text
CEO Room

Server Room
Meeting Room
```

Not every employee can enter every room.

For example:

```text
Employee
   ↓
Office Area

HR
   ↓
HR Area

System Administrator
   ↓
Server Room
```

Linux permissions work similarly.

```text
User
 ↓
Group
 ↓
Permission
 ↓
Resource
```

# 4. Linux Permission Model

Linux mainly evaluates access using:

```text
                File
                 │
        ┌────────┼────────┐
        ↓        ↓        ↓
      User     Group     Others
        │        │        │
        ↓        ↓        ↓
       rwx      rwx      rwx
```

For example:

```text
-rwxr-x---
```

Break it into:

```text
User
 ↓
rwx

Group
 ↓
r-x

Others
 ↓
---
```

---

# 5. Three Permission Categories

Linux permissions are divided into three categories:

| Category | Meaning |
|---|---|
| User | Owner of the file |
| Group | Group associated with the file |
| Others | Everyone else |

These are often represented as:

```text
u = user
g = group
o = others
```

Example:

```text
-rwxr-xr--
```

means:

```text
User   → rwx
Group  → r-x
Others → r--
```

---

# 6. Read Permission

Read is represented by:

```text
r
```

For a **file**, read means the user can view its contents.

Example:

```bash
cat application.log
```

For a **directory**, read generally means the user can list directory entries.

Example:

```bash
ls /var/log
```

---

# 7. Write Permission

Write is represented by:

```text
w
```

For a **file**, write means the user can modify its contents.

Example:

```bash
nano config.txt
```

For a **directory**, write generally means the user can create, delete, or rename entries inside the directory, subject to other permission checks.

This is an important distinction:

> Directory write permission is about modifying the directory's contents, not simply editing the contents of every file inside it.

---

# 8. Execute Permission

Execute is represented by:

```text
x
```

For a **file**, execute generally means the file can be executed as a program/script, assuming the file is otherwise usable.

Example:

```bash
./backup.sh
```

For a **directory**, execute means the user can traverse/access entries inside the directory when other permissions allow it.

For directories:

```text
r = list
w = create/delete/rename entries
x = traverse/access
```

This difference is extremely important for Linux administration.

---

# 9. Permissions for Files

Example:

```text
-rwxr-xr--
```

For a regular file:

```text
User:
rwx

Group:
r-x

Others:
r--
```

Meaning:

```text
Owner
→ Read
→ Write
→ Execute

Group
→ Read
→ Execute

Others
→ Read
```

---

# 10. Permissions for Directories

Consider:

```text
drwxr-x---
```

The first character:

```text
d
```

means directory.

Then:

```text
rwx
```

belongs to the owner.

```text
r-x
```

belongs to the group.

```text
---
```

belongs to others.

# 11. Understanding ls -l

Run:

```bash
ls -l
```

Example:

```text
-rw-r----- 1 rahul app-support 1200 Oct 20 10:30 application.log
```

Let's break it down.

```text
-rw-r----- 1 rahul app-support 1200 Oct 20 10:30 application.log
│ │  │      │    │      │         │          │
│ │  │      │    │      │         │          └── File
│ │  │      │    │      │         └── Date/time
│ │  │      │    │      └── Size
│ │  │      │    └── Group owner
│ │  │      └── User owner
│ │  └── Permissions
│ └── Permission structure
└── File type
```

The important section is:

```text
-rw-r-----
```

Break it into:

```text
- | rw- | r-- | ---
  |     |     |
  |     |     └── Others
  |     └──────── Group
  └────────────── User
```

---

# 12. File Ownership

Every file and directory has an owner.

Example:

```text
-rw-r----- 1 rahul app-support application.log
```

Here:

```text
Owner:
rahul

Group:
app-support
```

Ownership is important because permissions are evaluated based on the user, group, and others categories.

---

# 13. User Owner

The first ownership field represents the user owner.

Example:

```text
rahul
```

You can see ownership with:

```bash
ls -l
```

Example:

```text
-rw-r--r-- 1 rahul app-support application.log
```

---

# 14. Group Owner

The next ownership field represents the group owner.

Example:

```text
app-support
```

So:

```text
Owner → rahul
Group → app-support
```

Members of `app-support` can receive the group's permissions.

---

# 15. Others

`Others` means users who are neither:

- The file owner
- Members of the file's group

Example:

```text
-rw-r-----
```

Here:

```text
User   → rw-
Group  → r--
Others → ---
```

Users outside the owner/group categories have no permissions.

---

# 16. Permission Example

Consider:

```text
-rwxr-x---
```

Let's decode it.

```text
User:
rwx

Group:
r-x

Others:
---
```

Therefore:

| Category | Read | Write | Execute |
|---|---:|---:|---:|
| User | ✅ | ✅ | ✅ |
| Group | ✅ | ❌ | ✅ |
| Others | ❌ | ❌ | ❌ |

---

# 17. chmod

`chmod` means:

> **Change Mode**

It is used to change file and directory permissions.

Syntax:

```bash
chmod [permissions] filename
```

Example:

```bash
chmod 755 script.sh
```

---

# 18. Symbolic Permissions

Symbolic permissions use:

```text
u = user
g = group
o = others
a = all
```

Operations:

```text
+ = add
- = remove
= = set exactly
```

Examples:

```bash
chmod u+x script.sh
```

Add execute permission for the owner.

```bash
chmod g+w file.txt
```

Add write permission for the group.

```bash
chmod o-r file.txt
```

Remove read permission from others.

---

# 19. Numeric Permissions

Linux also allows numeric permission notation.

The values are:

```text
r = 4
w = 2
x = 1
```

Therefore:

```text
rwx = 4 + 2 + 1 = 7
rw- = 4 + 2 + 0 = 6
r-x = 4 + 0 + 1 = 5
r-- = 4 + 0 + 0 = 4
-w- = 0 + 2 + 0 = 2
--x = 0 + 0 + 1 = 1
--- = 0 + 0 + 0 = 0
```

---

# 20. Permission Values

| Permission | Numeric |
|---|---:|
| `---` | 0 |
| `--x` | 1 |
| `-w-` | 2 |
| `-wx` | 3 |
| `r--` | 4 |
| `r-x` | 5 |
| `rw-` | 6 |
| `rwx` | 7 |

# 22. chown

`chown` means:

> **Change Owner**

It changes the owner of a file or directory.

Syntax:

```bash
chown username filename
```

Example:

```bash
sudo chown rahul application.log
```

Check:

```bash
ls -l application.log
```

---

# 23. chgrp

`chgrp` means:

> **Change Group**

Syntax:

```bash
chgrp groupname filename
```

Example:

```bash
sudo chgrp app-support application.log
```

Check:

```bash
ls -l application.log
```

---

# 24. Changing User and Group Together

You can change both owner and group with `chown`.

Syntax:

```bash
sudo chown user:group file
```

Example:

```bash
sudo chown rahul:app-support application.log
```

Now:

```text
Owner:
rahul

Group:
app-support
```

This is extremely common in Linux administration.

---

# 25. Recursive Permissions

Sometimes a directory contains many files and subdirectories.

Example:

```text
/opt/myapp/
├── config/
├── logs/
├── scripts/
└── data/
```

You may need to change ownership recursively.

Example:

```bash
sudo chown -R rahul:app-support /opt/myapp
```

`-R` means:

> Recursive

It applies the operation to the directory and its contents.

### ⚠️ Production Warning

Be extremely careful with:

```bash
chown -R
chmod -R
```

Running them on the wrong directory can break an application or expose sensitive files.

Always verify the path first:

```bash
pwd
ls -ld /opt/myapp
```

---

# 26. Default Permissions

When a new file is created, Linux does not simply give it random permissions.

Default permissions are influenced by:

```text
Application defaults
+
umask
```

For example:

```bash
touch test.txt
```

Then:

```bash
ls -l test.txt
```

You might see:

```text
-rw-r--r--
```

The exact result depends on the process and current `umask`.

---

# 27. umask

`umask` controls which permission bits are removed from default permissions when new files and directories are created.

Check:

```bash
umask
```

Example:

```text
0022
```

You can also use:

```bash
umask -S
```

to see symbolic output.

Typical systems may use values such as:

```text
0022
0002
0077
```

depending on security and organizational configuration.

### Important

`umask` does not directly "set" final permissions in the same way `chmod` does.

It acts as a mask that removes permissions from the base permissions used by applications when creating new files/directories.

---

# 28. Special Permissions

Linux also provides special permission bits:

```text
SUID
SGID
Sticky Bit
```

These are especially useful in system administration.

---

# 29. SUID

SUID means:

> **Set User ID**

When applied to an executable file, it can cause the program to run with the effective privileges of the file owner.

Example:

```text
-rwsr-xr-x
```

Notice:

```text
s
```

instead of:

```text
x
```

A common example is:

```bash
ls -l /usr/bin/passwd
```

On many Linux systems, `passwd` uses SUID because changing a password requires access to protected authentication data.

### Security Warning

SUID programs must be carefully managed.

Do not add SUID casually.

---

# 30. SGID

SGID means:

> **Set Group ID**

SGID has important uses for both executable files and directories.

For a directory, SGID commonly causes newly created files/subdirectories to inherit the directory's group ownership.

Example:

```text
drwxrwsr-x
```

Notice:

```text
s
```

in the group execute position.

This is very useful for shared team directories.

Example:

```text
/opt/app-support/
```

where multiple support engineers need files to remain associated with:

```text
app-support
```

---

# 31. Sticky Bit

Sticky bit is commonly used on shared directories.

A classic example is:

```text
/tmp
```

Check:

```bash
ls -ld /tmp
```

You may see something similar to:

```text
drwxrwxrwt
```

The final:

```text
t
```

indicates the sticky bit.

It helps prevent users from deleting or renaming files in a shared directory that they do not own, subject to the directory's ownership and privilege rules.

---

# 32. Directory Permission Examples

Understanding directory permissions is extremely important.

Suppose:

```text
drwxr-x---
```

The owner has:

```text
rwx
```

The group has:

```text
r-x
```

Others have:

```text
---
```

For the directory:

```text
r → list directory entries
w → create/delete/rename entries
x → traverse/access entries
```

---

## Example

Suppose:

```text
/opt/app/logs
```

has:

```text
drwxr-x---
```

and:

```text
Owner: appuser
Group: app-support
```

Then:

```text
appuser
   ↓
rwx

app-support
   ↓
r-x

others
   ↓
---
```

Application Support users can potentially list and access entries, but cannot create/delete entries because they don't have directory write permission.

# 34. Permission Troubleshooting

One of the most common Application Support issues is:

```text
Permission denied
```

Example:

```bash
cat /opt/myapp/config/application.conf
```

Output:

```text
Permission denied
```

Don't immediately run:

```bash
sudo chmod 777
```

Instead investigate.

---

## Step 1 — Check Current User

```bash
whoami
```

---

## Step 2 — Check Groups

```bash
id
```

---

## Step 3 — Check File

```bash
ls -l /opt/myapp/config/application.conf
```

---

## Step 4 — Check Parent Directories

```bash
ls -ld /opt
ls -ld /opt/myapp
ls -ld /opt/myapp/config
```

A user needs appropriate traversal permissions on parent directories too.

---

## Step 5 — Check Ownership

Example:

```text
-rw-r----- 1 appuser app-support application.conf
```

Ask:

```text
Am I appuser?
       OR
Am I a member of app-support?
```

---

## Step 6 — Fix the Actual Problem

Maybe the user needs:

```text
Group membership
```

rather than:

```text
777 permission
```

# 35. sudo and Permissions

`sudo` can bypass many normal permission restrictions because it allows an authorized command to run with elevated privileges.

Example:

```bash
sudo cat /etc/shadow
```

However:

> `sudo` should not be the first solution to every permission problem.

Bad approach:

```bash
sudo chmod 777 file
```

Better approach:

```text
Understand ownership
        ↓
Understand group
        ↓
Understand permissions
        ↓
Give minimum required access
```

# 37. Application Support Example

Imagine an Application Support engineer receives this ticket:

```text
INC-1042

Application Support cannot read production logs.

Error:
Permission denied

File:
/opt/myapp/logs/application.log
```

A beginner might run:

```bash
chmod 777 application.log
```

This is a bad production approach.

A better investigation is:

```bash
whoami
```

Then:

```bash
id
```

Then:

```bash
ls -l /opt/myapp/logs/application.log
```

Then:

```bash
ls -ld /opt/myapp
ls -ld /opt/myapp/logs
```

Suppose we discover:

```text
Owner:
appuser

Group:
app-support
```

and the support engineer is not a member of:

```text
app-support
```

The actual fix may be to request/add the user to the approved group rather than changing the file to `777`.

This demonstrates an important production mindset:

> **Fix the access model, not just the immediate error.**


```bash
ls -l /opt/myapp/logs
```


```bash
cat /opt/myapp/logs/application.log
```

---

```bash
sudo bash -c 'echo "#!/bin/bash" > /opt/myapp/scripts/backup.sh'
```


Make executable:

```bash
sudo chmod 750 /opt/myapp/scripts/backup.sh
```

---

## Step 12 — Test Script

```bash
sudo -u appuser /opt/myapp/scripts/backup.sh
```

Expected:

```text
Backup completed
```

This demonstrates how ownership and execute permissions affect application/service users.

# 40. Common Mistakes

## Mistake 1 — Using chmod 777 Everywhere

Avoid:

```bash
chmod 777 file
```

unless there is a very specific, justified reason and it is appropriate for the environment.

`777` means:

```text
User:
rwx

Group:
rwx

Others:
rwx
```

This grants very broad access.

---

## Mistake 2 — Using chown -R Without Checking

Dangerous:

```bash
sudo chown -R user:group /
```

Never do this.

Always verify the path.

---

## Mistake 3 — Confusing File and Directory Permissions

Remember:

```text
File:
r → read contents
w → modify contents
x → execute

Directory:
r → list
w → create/delete/rename entries
x → traverse/access
```

---

## Mistake 4 — Forgetting Group Membership

If a user should access a shared directory:

```text
Check group membership
```

using:

```bash
id username
```

---

## Mistake 5 — Forgetting Parent Directory Permissions

A file may have:

```text
-rw-r-----
```

but the user may still receive:

```text
Permission denied
```

because they cannot traverse one of the parent directories.

---

# 41. Security Best Practices

## 1. Follow Least Privilege

Give users only the access they need.

---

## 2. Avoid 777

Prefer specific:

```text
Owner
Group
Permissions
```

---

## 3. Use Groups

For shared access:

```text
Users
   ↓
Group
   ↓
Permissions
```

---

## 4. Protect Configuration Files

Configuration files may contain:

- Database credentials
- API keys
- Tokens
- Internal endpoints
- Application settings

Do not expose them unnecessarily.

---

## 5. Be Careful with SUID/SGID

Special permissions can have security implications.

---

## 6. Verify Before Changing Production

Before:

```bash
chmod
chown
chgrp
```

check:

```bash
pwd
ls -ld target
ls -l target
```

---

## 7. Use Change Management

In production, permission changes should normally be associated with an approved ticket/change process.

# 🧠 The Most Important Concept

Remember this diagram:

```text
                    FILE / DIRECTORY
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
           USER          GROUP         OTHERS
             │             │             │
             ↓             ↓             ↓
            rwx           rwx           rwx
```

Linux first identifies the user and then evaluates the applicable permission category.

When you see:

```text

```

don't immediately think:

```bash

```

Think:

```text
Who am I?
     ↓
What groups am I in?
     ↓
Who owns the file?
     ↓
What group owns the file?
     ↓
What are the permissions?
     ↓
What are the parent-directory permissions?
     ↓
What access is actually required?
     ↓
```
