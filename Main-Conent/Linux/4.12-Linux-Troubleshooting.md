# 🐧 Linux Troubleshooting

> **Module 4 → 4.12 Linux Troubleshooting**

Linux troubleshooting is one of the most important skills for an **Application Support Engineer, DevOps Engineer, Cloud Engineer, and System Administrator**.

In a real production environment, applications can fail for many different reasons:

- Server is down
- CPU is high
- Memory is exhausted
- Disk is full
- Application process stopped
- Service failed
- Port is not listening
- Network is unavailable
- DNS is not resolving
- File permissions are wrong
- Application logs contain errors
- Database connection is failing
- Configuration is incorrect
- A recent deployment introduced a problem

The goal of troubleshooting is not to randomly run commands.

The goal is:

```text
Understand
   ↓
Collect Evidence
   ↓
Identify the Problem
   ↓
Find the Root Cause
   ↓
Take Safe Action
   ↓
Validate
   ↓
Document
```

# 1. What is Troubleshooting?

**Troubleshooting** is the systematic process of finding and resolving a problem.

For example:

> Application is not working.

This statement is not enough.

We need to investigate.

Maybe:

```text
Application
     ↓
Process
     ↓
Service
     ↓
Port
     ↓
Network
     ↓
Server
     ↓
Database
```

We need to identify where the failure is occurring.

---

# 2. Why Linux Troubleshooting Matters

Many production applications run on Linux.

For example:

```text
User
  ↓
Load Balancer
  ↓
Linux Application Server
  ↓
Linux Database Server
  ↓
Storage
```

If the application becomes unavailable, the support engineer may need to investigate the Linux server.

Typical questions:

```text
Is the server reachable?

Is the application running?

Is the service running?

Is the port listening?

Is CPU high?

Is memory available?

Is disk full?

Are there errors in logs?

Can the application connect to the database?

Did someone recently change something?
```

---

# 3. Troubleshooting Mindset

A beginner often does this:

```text
Application not working
        ↓
Restart service
        ↓
Still not working
        ↓
Restart server
        ↓
Still not working
```

This is not good troubleshooting.

A professional approach is:

```text
Problem
  ↓
Evidence
  ↓
Hypothesis
  ↓
Test
  ↓
Result
  ↓
Root Cause
  ↓
Safe Fix
  ↓
Validation
```

---

# 4. The Troubleshooting Lifecycle

A useful troubleshooting lifecycle is:

```text
1. Understand
      ↓
2. Reproduce / Confirm
      ↓
3. Collect Evidence
      ↓
4. Narrow Down
      ↓
5. Identify Root Cause
      ↓
6. Fix
      ↓
7. Validate
      ↓
8. Document
```

---

# 5. Step 1 — Understand the Problem

Before running commands, understand the incident.

Ask:

### What happened?

Example:

```text
Application is unavailable.
```

### When did it happen?

```text
10:30 AM
```

### Who is affected?

```text
All customers
```

or:

```text
Only some users
```

### What changed?

Check:

- Deployment
- Configuration
- Package update
- Infrastructure change
- Database change
- Network change

### Is it reproducible?

Try to verify the problem.

---

# 6. Step 2 — Check Server Availability

First determine whether the server is reachable.

From another machine:

```bash
ping SERVER_IP
```

Example:

```bash
ping 10.10.20.50
```

However, remember:

> Ping can fail even when SSH or an application is reachable because ICMP may be blocked.

So also test the actual required port.

```bash
nc -vz 10.10.20.50 22
```

For an application:

```bash
nc -vz 10.10.20.50 8080
```

---

# 7. Step 3 — Check System Information

After connecting:

```bash
hostname
```

```bash
hostnamectl
```

Check kernel:

```bash
uname -a
```

Check uptime:

```bash
uptime
```

Check logged-in users:

```bash
who
```

Check current user:

```bash
whoami
```

Check OS information:

```bash
cat /etc/os-release
```

---

# 8. Step 4 — Check CPU

High CPU can make applications slow or unavailable.

Start with:

```bash
top
```

or:

```bash
htop
```

Check CPU information:

```bash
lscpu
```

Check load:

```bash
uptime
```

Example:

```text
load average: 8.50, 7.20, 6.80
```

Load average should be interpreted relative to the number of CPU cores and workload.

---

## Find CPU-Heavy Processes

```bash
ps aux --sort=-%cpu | head
```

Example:

```text
USER    PID   %CPU
app     1234  95.2
root    2345  40.1
```

The application process may be consuming excessive CPU.

---

# 9. Step 5 — Check Memory

Check memory:

```bash
free -h
```

Example:

```text
               total   used   free
Mem:           16Gi    14Gi   500Mi
```

Check processes:

```bash
ps aux --sort=-%mem | head
```

---

## Important Concept

Do not assume:

```text
free = available memory
```

Linux uses memory for:

- Processes
- Cache
- Buffers
- Kernel
- Other system functions

`free -h` provides a more useful overview.

---

# 10. Step 6 — Check Disk

Check filesystem usage:

```bash
df -h
```

Example:

```text
Filesystem      Size  Used Avail Use%
/dev/sda1        50G   49G  500M  99%
```

A filesystem at 99% usage is a serious problem.

---

## Find Large Directories

```bash
du -sh /*
```

Better:

```bash
du -sh /var/* 2>/dev/null
```

For logs:

```bash
du -sh /var/log/*
```

Find large files:

```bash
find /var -type f -size +500M 2>/dev/null
```

---

# 11. Step 7 — Check Processes

List processes:

```bash
ps aux
```

Another format:

```bash
ps -ef
```

Find an application:

```bash
ps aux | grep myapp
```

Better:

```bash
pgrep -af myapp
```

Process tree:

```bash
pstree
```

---

## Important Questions

Ask:

```text
Is the process running?

Who owns it?

What PID does it have?

How much CPU is it using?

How much memory is it using?

What command started it?
```

---

# 12. Step 8 — Check Services

Check a service:

```bash
systemctl status myapp
```

Check failed services:

```bash
systemctl --failed
```

Start:

```bash
sudo systemctl start myapp
```

Restart:

```bash
sudo systemctl restart myapp
```

But:

> Never restart a production service just because it is the first command you remember.

First investigate.

---

## Check Service Logs

```bash
journalctl -u myapp -n 100
```

Follow:

```bash
journalctl -u myapp -f
```

# 13. Step 9 — Check Ports

Applications normally listen on network ports.

Check:

```bash
ss -lntp
```

Example:

```text
LISTEN 0 128 0.0.0.0:8080
```

This tells us something is listening on port `8080`.

Search for a specific port:

```bash
ss -lntp | grep ':8080'
```

# 15. Step 11 — Check DNS

Test hostname resolution:

```bash
nslookup example.com
```

or:

```bash
dig example.com
```

or:

```bash
host example.com
```

Test:

```bash
getent hosts example.com
```

---

## Example Problem

Application tries:

```text
database.company.internal
```

but DNS cannot resolve it.

Test:

```bash
nslookup database.company.internal
```

If resolution fails, investigate DNS before changing application configuration.

# 16. Step 12 — Check Logs

Logs are one of the most important troubleshooting sources.

Common locations:

```text
/var/log/
```

List logs:

```bash
ls -lh /var/log/
```

View:

```bash
less /var/log/syslog
```

On some RHEL-family systems:

```bash
less /var/log/messages
```

Application-specific logs may be somewhere like:

```text
/var/log/myapp/
```

---

## Search Logs

Use:

```bash
grep "ERROR" application.log
```

Case-insensitive:

```bash
grep -i "error" application.log
```

Search multiple keywords:

```bash
grep -Ei "error|failed|exception" application.log
```

---

## Follow Live Logs

```bash
tail -f application.log
```

This is useful when reproducing a problem.

---

# 17. Step 13 — Check File Permissions

A service may fail because it cannot read or write a file.

Check:

```bash
ls -l /path/to/file
```

Example:

```text
-rw-r----- 1 appuser appgroup application.conf
```

Check directory:

```bash
ls -ld /path/to/directory
```

Check ownership:

```bash
stat /path/to/file
```

Change ownership only when appropriate:

```bash
sudo chown appuser:appgroup /path/to/file
```

Change permissions only after understanding the requirement:

```bash
sudo chmod 640 /path/to/file
```

---

# 18. Step 14 — Check Environment Variables

An application may depend on environment variables.

Check:

```bash
env
```

Specific variable:

```bash
echo $JAVA_HOME
```

Check PATH:

```bash
echo $PATH
```

Check shell:

```bash
echo $SHELL
```

---

## Common Production Problem

The application works manually:

```bash
./start.sh
```

but fails through systemd.

Why?

The environment may be different.

For example:

```text
Manual Shell
   ↓
JAVA_HOME exists
   ↓
Application works

systemd
   ↓
JAVA_HOME missing
   ↓
Application fails
```

This is why environment troubleshooting is important.

---

# 19. Step 15 — Check Recent Changes

One of the most useful troubleshooting questions is:

> **What changed?**

Check:

- Application deployment
- Configuration
- Package updates
- Server changes
- DNS changes
- Firewall changes
- Database changes
- Certificate changes
- Environment variables
- Infrastructure changes

A useful production principle is:

```text
Problem started after Change
             ↓
Investigate Change
```

But do not automatically assume the latest change is the root cause. Verify it with evidence.

# 21. High CPU Troubleshooting

## Symptom

Application is slow.

Check:

```bash
top
```

Then:

```bash
ps aux --sort=-%cpu | head
```

Find process:

```bash
pgrep -af myapp
```

Check process details:

```bash
ps -p PID -o pid,ppid,user,%cpu,%mem,etime,cmd
```

---

## Questions

```text
Which process is using CPU?

Has CPU increased recently?

Is the process expected to consume CPU?

Is traffic higher than normal?

Is there an infinite loop?

Did a deployment happen?

Are multiple instances affected?
```

Do not immediately kill the process.

# 22. High Memory Troubleshooting

Check:

```bash
free -h
```

Then:

```bash
ps aux --sort=-%mem | head
```

Find top memory consumers.

Check:

```bash
top
```

Possible causes:

- Memory leak
- Increased traffic
- Large cache
- Too many processes
- Incorrect application configuration
- Unexpected workload

---

# 23. Disk Full Troubleshooting

## Symptom

Application cannot write files.

Possible error:

```text
No space left on device
```

First:

```bash
df -h
```

Then:

```bash
df -i
```

Why check inode usage?

Because a filesystem can have free disk space but still run out of inodes.

---

## Find Large Directories

```bash
du -xhd1 /var 2>/dev/null
```

Then investigate:

```bash
du -xhd1 /var/log 2>/dev/null
```

Find large files:

```bash
find /var -xdev -type f -size +500M -ls 2>/dev/null
```

---

## Important

Do not blindly delete:

```text
/var/log/*
```

from production.

Follow your organization's log-retention and cleanup procedure.

# 24. Service Down Troubleshooting

Suppose:

```bash
systemctl status myapp
```

shows:

```text
failed
```

Do not immediately restart.

First:

```bash
journalctl -u myapp -n 100
```

Check:

```bash
systemctl cat myapp
```

Check:

```bash
systemctl show myapp
```

Check configuration.

Check dependencies.

Check ports.

Check disk.

Check permissions.

Then decide the appropriate action.

# 25. Port Not Listening

Suppose application should listen on:

```text
8080
```

Check:

```bash
ss -lntp | grep ':8080'
```

Nothing appears.

Possible causes:

- Application is not running
- Wrong configuration
- Application crashed
- Wrong port
- Binding only to localhost
- Startup failed

Check service:

```bash
systemctl status myapp
```

Check logs:

```bash
journalctl -u myapp -n 100
```

# 26. Connection Refused

Example:

```text
Connection refused
```

Meaning:

Check:


Check service:

```bash

```

Check firewall.

Check application configuration.

# 29. Permission Problems

Example:

```text
Permission denied
```

Check:

```bash
ls -l file
```

Then:

```bash
id
```

Check directory permissions:

```bash
namei -l /path/to/file
```

This is useful because access to a file depends not only on the file itself but also on directory permissions along the path.

Check ACLs if applicable:

```bash
getfacl file
```

# 30. Application Log Errors

Suppose logs show:

```text
ERROR Database connection failed
```

Do not immediately restart the application.

Investigate:

```text
Application
   ↓
Database Host
   ↓
DNS
   ↓
Network
   ↓
Database Port
   ↓
Authentication
   ↓
Database
```

Test DNS:

```bash
getent hosts dbserver
```

Test port:

```bash
nc -vz dbserver 5432
```

For MySQL:

```text
3306
```

For PostgreSQL:

```text
5432
```

Then investigate credentials/configuration and database health according to the team's procedures.

# 31. Process Problems

A process may:

- Stop unexpectedly
- Consume CPU
- Consume memory
- Become stuck
- Spawn too many children
- Hold a port
- Hold files open

Find process:

```bash
pgrep -af myapp
```

Check:

```bash
ps -p PID -o pid,ppid,user,%cpu,%mem,stat,etime,cmd
```

Check open files:

```bash
lsof -p PID
```

Check which process uses a port:

```bash
sudo lsof -i :8080
```

or:

```bash
ss -lntp | grep ':8080'
```

Suppose:

```text

    |

    |

```

# 34. Production Troubleshooting Example

## Incident

```text
INC003421

Customers are unable to place orders.

Severity: High
```

Architecture:

```text
Customer
   ↓
Load Balancer
   ↓
Order Service
   ↓
Database
```

---

## Step 1 — Confirm

Try the application.

Check monitoring.

Check whether all users are affected.

---

## Step 2 — Connect

```bash
ssh supportuser@order-server
```

---

## Step 3 — Check Server

```bash
hostname
uptime
```

---

## Step 4 — Check CPU

```bash
top
```

Result:

```text
CPU normal
```

Continue.

---

## Step 5 — Check Memory

```bash
free -h
```

Result:

```text
Memory normal
```

Continue.

---

## Step 6 — Check Disk

```bash
df -h
```

Result:

```text
/var = 98%
```

Investigate:

```bash
du -xhd1 /var 2>/dev/null
```

Result:

```text
/var/log = 45G
```

Investigate:

```bash
du -sh /var/log/*
```

Find a very large application log.

---

## Step 7 — Check Application

```bash
systemctl status order-service
```

Service is running.

Check logs:

```bash
journalctl -u order-service -n 100
```

Logs show:

```text
No space left on device
```

---

## Root Cause

The application could not write required files because the filesystem was nearly full.

---

## Action

Follow the approved production log-management procedure.

Do not randomly delete files.

After cleanup/rotation:

```bash
df -h
```

Then validate application health.

---

## Final Incident Update

```text
Incident: INC003421

Issue:
Customers were unable to place orders.

Investigation:
Application server was reachable and application service was running.
CPU and memory were normal.

Finding:
The /var filesystem reached critical utilization.
Application logs consumed most available disk space.

Action:
Approved log cleanup/rotation procedure was performed.

Validation:
Disk utilization returned to normal.
Application health checks passed.
Order creation was successfully validated.

Status:
Resolved.
```

This is a good example of evidence-based troubleshooting.

# 35. Troubleshooting Decision Tree

Use this general decision tree:

```text
             Application Problem
                    |
                    ↓
             Is server reachable?
              /             \
            NO               YES
            |                 |
       Network/Host       Check Server
                              |
                              ↓
                       CPU / Memory / Disk
                              |
                              ↓
                       Is process running?
                         /          \
                       NO            YES
                       |              |
                  Check Service    Check Port
                                      |
                                      ↓
                              Is port listening?
                                /          \
                              NO            YES
                              |              |
                       Check App/Config   Check Network
                                             |
                                             ↓
                                         Check DNS
                                             |
                                             ↓
                                         Check Logs
                                             |
                                             ↓
                                     Check Dependencies
                                             |
                                             ↓
                                       Find Root Cause
```

# 41. Common Troubleshooting Mistakes

## Mistake 1 — Restarting Everything

Bad approach:

```text
Problem
↓
Restart application
↓
Restart server
↓
Restart database
```

Why it is bad:

- Root cause may remain
- Evidence can disappear
- Downtime may increase
- Production impact can increase

---

# Mistake 2 — Deleting Logs Blindly

Never do:

```bash
rm -rf /var/log/*
```

This can cause serious problems.

Follow approved log rotation/cleanup procedures.

---

# Mistake 3 — Using `kill -9` Immediately

Avoid:

```bash
kill -9 PID
```

unless there is a justified reason.

Prefer graceful termination where appropriate:

```bash
kill -15 PID
```

---

# Mistake 4 — Changing Permissions Randomly

Avoid:

```bash
chmod -R 777 /application
```

This is a common but dangerous "fix."

Find the actual ownership and permission requirement.

---

# Mistake 5 — Assuming Every Error is an Application Error

A message like:

```text
Database connection failed
```

may actually be caused by:

```text
DNS
Network
Firewall
Port
Credentials
Database
```

Always investigate the complete path.

---

# Mistake 6 — No Evidence

Do not write:

```text
Issue fixed.
```

Write:

```text
Disk utilization reached 98%.
Application logs consumed 45 GB.
Approved log rotation was performed.
Disk utilization reduced to 61%.
Application health check passed.
```

Evidence makes troubleshooting professional.

---

# Mistake 7 — Ignoring Recent Changes

Always ask:

> What changed before the issue started?

But verify the relationship rather than assuming causation.

---

```text
        ↓

        ↓

```

---

## Rule 5

## Rule 6
