# 1. Introduction

When working with Linux, you frequently see commands such as:

```bash
pwd
ls
cd
echo
export
printenv
```

Behind many Linux commands and applications are **variables**.

Variables allow us to store information such as:

```text
Username
Home directory
Current directory
Shell
Executable search paths
Application configuration
Database connection information
Environment-specific settings
```

For example:

```bash
echo $USER
```

might return:

```text
sahil
```

Another example:

```bash
echo $HOME
```

might return:

```text
/home/sahil
```

These values are provided through the shell environment.

Environment variables are extremely important in:

- Linux administration
- Application Support
- DevOps
- Cloud
- CI/CD
- Docker
- Kubernetes
- Application configuration
- Shell scripting

---

# 2. What is a Shell?

A **shell** is a program that allows a user to interact with the operating system using commands.

For example:

```bash
ls
```

The shell receives the command and executes the appropriate program.

A simplified flow is:

```text
User
  ↓
Terminal
  ↓
Shell
  ↓
Operating System
  ↓
Kernel
  ↓
Hardware
```

Example:

```bash
ls -l /var/log
```

The shell interprets the command and starts the required program.

---

# 3. Why Do We Need a Shell?

A shell provides an interface between the user and the operating system.

Without a shell, interacting with a Linux system from the command line would be much harder.

The shell allows us to:

- execute commands
- run programs
- create variables
- use environment variables
- redirect output
- use pipes
- create scripts
- automate tasks
- control processes
- work with files
- configure applications

For Application Support engineers, the shell is one of the most important tools.

---

# 4. Shell vs Terminal

These two terms are often confused.

## Terminal

A **terminal** is the interface/application through which you interact with the shell.

Examples:

```text
GNOME Terminal
Konsole
Windows Terminal
macOS Terminal
```

## Shell

The shell is the program that interprets commands.

Examples:

```text
Bash
Zsh
Fish
Ksh
sh
```

Think of it like:

```text
Terminal
   ↓
provides the window/interface

Shell
   ↓
interprets your commands
```

For example:

```text
GNOME Terminal
      ↓
    Bash
      ↓
    Linux
```

# 7. How Bash Works

Suppose you type:

```bash
ls -l
```

The process can be simplified as:

```text
User enters command
        ↓
Bash receives command
        ↓
Bash interprets command
        ↓
Bash finds executable
        ↓
Program executes
        ↓
Output returned to terminal
```

Another example:

```bash
echo $HOME
```

Bash first expands:

```text
$HOME
```

into something like:

```text
/home/sahil
```

Then executes:

```bash
echo /home/sahil
```

# 8. Shell Prompt

A typical Linux prompt may look like:

```text
sahil@server01:~$
```

Let's understand it.

```text
sahil
```

Current user.

```text
@
```

Separator.

```text
server01
```

Hostname.

```text
:
```

Separator.

```text
~
```

Current directory, where `~` means the user's home directory.

```text
$
```

Normal user prompt.

For root, you may see:

```text
#
```

Example:

```text
root@server01:/var/log#
```

### Important

Do not confuse:

```text
$
```

with the `$` used when accessing a variable.

Example:

```bash
$USER
```

Here `$USER` means variable expansion.

# 11. Environment Variables

An **environment variable** is a variable that is available to processes started from the environment where it was exported.

Examples:

```text
PATH

SHELL
PWD

```

Check:

```bash
printenv
```

```bash

```

---

# 12. Shell Variables vs Environment Variables

This distinction is important.

### Shell Variable

```bash
name="Sahil"
```

This variable belongs to the current shell.

### Environment Variable

```bash
export name="Sahil"
```

Now child processes can inherit it.

Think:

```text
Current Shell
     │
     ├── shell variables
     │
     └── exported environment variables
              │
              ▼
        Child Processes
```

# 14. The PATH Variable

`PATH` is one of the most important environment variables.

Example:

```bash
echo $PATH
```

Output:

```text
/usr/local/bin:/usr/bin:/bin
```

The directories are separated by:

```text
:
```

When you execute:

```bash
curl
```

the shell searches the directories in `PATH`.

Simplified:

```text
curl
 ↓
/usr/local/bin/curl ?
 ↓
/usr/bin/curl ?
 ↓
/bin/curl ?
```

The first matching executable is used.

---

## Why PATH Matters

Suppose an application requires:

```text
java
```

but you get:

```text
java: command not found
```

Possible causes include:

```text
Java not installed
Java installed but not in PATH
Incorrect PATH
Wrong Java version
Different environment
```

# 17. Exporting Variables

A normal shell variable:

```bash
name="Sahil"
```

Export it:

```bash
export name
```

Or directly:

```bash
export name="Sahil"
```

Now child processes can access it.

## Example

Create:

```bash
export APP_ENV="production"
```

Check:

```bash
echo $APP_ENV
```

Output:

```text
production
```

## Child Process Example

Run:

```bash
export APP_ENV="production"
bash
```

Inside the new shell:

```bash
echo $APP_ENV
```

Output:

```text
production
```

The child shell inherited the exported variable.

# 18. Temporary vs Permanent Variables

This is very important for Application Support.

## Temporary Variable

Run:

```bash
export APP_ENV="production"
```

It exists for the current shell session and processes started from it.

After logging out or starting a new independent session, it may no longer exist.

---

## Permanent Variable

To make variables available when a user starts a new shell, configuration files such as:

```text
~/.bashrc
~/.profile
~/.bash_profile
```

may be used depending on the shell/session type.

Example:

```bash
export APP_ENV="development"
```

inside an appropriate startup file.

Then reload it:

```bash
source ~/.bashrc
```

---

# 19. `.bashrc`

`.bashrc` is a Bash startup configuration file commonly used for interactive non-login Bash shells.

Location:

```text
~/.bashrc
```

Example:

```bash
nano ~/.bashrc
```

Add:

```bash
export APP_ENV="development"
```

Save.

Then:

```bash
source ~/.bashrc
```

Check:

```bash
echo $APP_ENV
```

Output:

```text
development
```

# 20. `.profile`

A user's `.profile` file can be used for environment setup during login sessions.

Location:

```text
~/.profile
```

Example:

```bash
nano ~/.profile
```

You might add:

```bash
export APP_ENV="development"
```

The exact startup-file behavior depends on how the shell/session is started.

---

# 21. `.bash_profile`

`.bash_profile` is commonly associated with Bash login shells.

Location:

```text
~/.bash_profile
```

On systems where it exists, Bash may use it for login-shell initialization.

A common pattern is to have it load `.bashrc`:

```bash
if [ -f ~/.bashrc ]; then
    . ~/.bashrc
fi
```

This keeps interactive Bash configuration in one place.

---

# 22. Shell Startup Files

Different situations may load different files.

A simplified view:

```text
Login Shell
    │
    ├── ~/.bash_profile
    │       │
    │       └── may load ~/.bashrc
    │
    └── ~/.profile

Interactive Non-Login Bash
    │
    └── ~/.bashrc
```

Do not assume that every file is always loaded.

When troubleshooting an environment variable, first determine:

```text
Which user?
Which shell?
Login or non-login shell?
Interactive or non-interactive?
```

# 23. Changing PATH

Suppose you have a custom executable directory:

```text
/home/sahil/tools
```

You can temporarily add it:

```bash
export PATH="$PATH:/home/sahil/tools"
```

Check:

```bash
echo $PATH
```

Then:

```bash
which mycommand
```

if `mycommand` exists there.

---

## Why Use `$PATH`?

This:

```bash
export PATH="$PATH:/home/sahil/tools"
```

preserves the existing PATH.

Be careful with:

```bash
export PATH="/home/sahil/tools"
```

because this replaces the existing PATH and can cause standard commands to stop working.

# 26. Variable Expansion

Bash can substitute variables into commands.

Example:

```bash
name="Sahil"
echo "Hello $name"
```

Output:

```text
Hello Sahil
```

Another example:

```bash
app="payment"
echo "Application: $app"
```

Output:

```text
Application: payment
```

---

## Braces

Sometimes use:

```bash
name="Sahil"
echo "${name}"
```

Braces are especially useful when adding text immediately after a variable.

Example:

```bash

```

Output:

```text

```

---

# 27. Quoting in Bash

Quoting is very important in shell commands.

## Double Quotes

```bash
name="Sahil"
echo "Hello $name"
```

Variables are expanded.

Output:

```text
Hello Sahil
```

---

## Single Quotes

```bash
echo 'Hello $name'
```

Output:

```text
Hello $name
```

Variables are generally not expanded inside single quotes.

---

## No Quotes

```bash
echo $name
```

This works for simple values but can cause problems when values contain spaces or special characters.

Prefer quoting variable expansions when appropriate:

```bash
echo "$name"
```

# 28. Command Substitution

Command substitution allows you to store command output inside another command.

Modern syntax:

```bash
$(command)
```

Example:

```bash
current_date=$(date)
echo "$current_date"
```

Another example:

```bash
hostname_value=$(hostname)
echo "Server: $hostname_value"
```

Output:

```text
Server: server01
```

This is extremely useful in shell scripts.

# 29. Exit Status

Every command returns an exit status.

Usually:

```text
0 = success
non-zero = failure
```

Check the previous command's exit status using:

```bash
echo $?
```

Example:

```bash
ls
echo $?
```

If successful:

```text
0
```

---

## Example of Failure

```bash
ls /directory-that-does-not-exist
echo $?
```

You may receive a non-zero value.

This is very important in automation and Application Support.

# 30. Shell Operators

Bash supports useful operators.

### `&&`

Run the second command only if the first succeeds.

```bash
mkdir test && cd test
```

---

### `||`

Run the second command if the first fails.

```bash
cd /wrong/path || echo "Directory not found"
```

---

### `;`

Run commands sequentially regardless of previous success.

```bash
echo "Hello"; date
```

---

# 31. Command Chaining

Example:

```bash
mkdir application && cd application && pwd
```

Flow:

```text
mkdir application
       ↓ success
cd application
       ↓ success
pwd
```

If `mkdir` fails, the next command will not execute because of `&&`.

---

## Real Support Example

Check a service and show logs only if the service is running:

```bash
systemctl is-active nginx && journalctl -u nginx -n 20
```

This is useful when creating troubleshooting commands and scripts.

# 36. Application Support Scenarios

## Scenario 1 — Application Says Command Not Found

Suppose:

```bash
java
```

returns:

```text
java: command not found
```

Investigate:

```bash
which java
```

Then:

```bash
echo $PATH
```

Check Java installation.

```bash
find /usr /opt -name java 2>/dev/null
```

If Java exists but is not in PATH, investigate the intended environment configuration.

---

# Scenario 2 — Works Manually but Fails from Service

This is a very common production problem.

Developer says:

> "The application works when I run it manually, but it fails when started as a systemd service."

One possible reason:

```text
Interactive shell
       ↓
loads environment
       ↓
PATH/configuration available

systemd service
       ↓
different environment
```

Check:

```bash
systemctl show application.service --property=Environment
```

Also inspect the unit file and service configuration.

Do not assume the service has the same environment as your login shell.

---

# Scenario 3 — Different PATH

Run:

```bash
echo $PATH
```

Then compare with the application's/service environment.

A command may work for:

```text
supportuser
```

but fail for:

```text
application-service-user
```

because they have different environments.

---

# Scenario 4 — Wrong Application Environment

Application expected:

```text
APP_ENV=production
```

but shows:

```text
APP_ENV=development
```

Check:

```bash
echo $APP_ENV
```

Then investigate where the variable is being set:

```text
~/.bashrc
~/.profile
service configuration
deployment configuration
CI/CD pipeline
container configuration
```

---

# Scenario 5 — Port Configuration

Application expects:

```text
PORT=8080
```

Check:

```bash
echo $PORT
```

If empty:

```bash
printenv PORT
```

Then investigate application configuration.

Never assume an empty variable is automatically the root cause.

# 38. Troubleshooting Environment Variables

## Problem 1 — Variable Is Empty

Run:

```bash
echo "$APP_ENV"
```

If empty, check:

```bash
printenv APP_ENV
```

Then determine:

```text
Was it exported?
Was it defined?
Was the startup file loaded?
Is this the correct user?
Is this the correct shell?
```

---

# Problem 2 — Variable Exists in One Session but Not Another

Possible reasons:

```text
Temporary variable
Different user
Different shell
Different startup file
Login vs non-login shell
Interactive vs non-interactive shell
```

Check:

```bash
whoami
echo $SHELL
echo $APP_ENV
```

---

# Problem 3 — PATH Is Broken

If standard commands suddenly stop working:

```bash
echo $PATH
```

If PATH was accidentally replaced with something like:

```text
/home/user/tools
```

standard commands may fail.

A typical Linux PATH contains directories such as:

```text
/usr/local/bin
/usr/bin
/bin
```

Restore the environment carefully based on your distribution and shell configuration.

---

# Problem 4 — `.bashrc` Changes Are Not Working

After editing:

```bash
~/.bashrc
```

run:

```bash
source ~/.bashrc
```

Then:

```bash
echo $APP_ENV
```

If it still does not work, check:

```bash
echo $SHELL
```

and determine whether `.bashrc` is actually being loaded for the session.

---

# Problem 5 — Works Manually but Not as Service

Check the service:

```bash
systemctl status application.service
```

Inspect its environment:

```bash
systemctl show application.service --property=Environment
```

Inspect the unit file:

```bash
systemctl cat application.service
```

Remember:

> A systemd service does not automatically have the exact same environment as your interactive login shell.

# 39. Security Considerations

Environment variables are convenient, but they are **not automatically secure storage**.

Avoid casually storing sensitive information such as:

```text
Passwords
Private keys
API secrets
Database credentials
Access tokens
```

in easily readable shell startup files.

For example, avoid:

```bash
export DB_PASSWORD="my-password"
```

in a shared or insecure environment.

Production systems should use appropriate secret-management mechanisms and access controls.

---

## Be Careful with Logs

Never accidentally print secrets:

```bash
echo "$DB_PASSWORD"
```

and never put secrets into debugging output unless your organization's security policy explicitly permits it.

---

## Principle

Use environment variables for configuration, but treat sensitive values carefully.

```text
Configuration
      ↓
Environment variable

Sensitive secret
      ↓
Use approved secret-management mechanism
```
