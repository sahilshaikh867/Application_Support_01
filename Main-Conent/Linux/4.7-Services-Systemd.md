# 1. Introduction

A Linux server can run many applications and background services.

For example:

```text
Linux Server
│
├── SSH
├── Nginx
├── Application Server
├── Database
├── Monitoring Agent
├── Logging
├── Cron
└── Backup Service
```

These applications often need to:

- start automatically
- run continuously
- restart when necessary
- stop safely
- start after server reboot
- generate logs
- depend on other services

Linux uses **service management systems** to handle these requirements.

On most modern Linux distributions, the primary system and service manager is:

```text
systemd
```

The main command used to interact with it is:

```bash
systemctl
```

---

# 2. What is a Service?

A **service** is a background application or process that performs a specific function, usually without requiring direct user interaction.

Examples:

```text
SSH Service
Web Server
Database Service
Docker Service
Logging Service
Monitoring Service
```

For example:

```text
sshd
```

provides SSH access.

A web server such as Nginx provides HTTP/HTTPS traffic handling.

---

# 3. Program vs Process vs Service

These three concepts are related but different.

| Concept | Meaning |
|---|---|
| Program | Software stored on disk |
| Process | Running instance of a program |
| Service | A managed background application/process providing a function |

Example:

```text
nginx program
     ↓
nginx process
     ↓
nginx service
```

A service can be managed by `systemd`.

---

# 4. Why Services are Required

Imagine a production server running an e-commerce application.

After a server reboot:

```text
Server shuts down
       ↓
Server starts
       ↓
Linux boots
       ↓
Application should start
       ↓
Users can access website
```

Without proper service management, administrators might have to manually start every application.

With systemd:

```text
Server Boot
    ↓
systemd
    ↓
Start required services
    ↓
Application available
```

Services provide:

- automatic startup
- controlled shutdown
- restart policies
- dependency management
- status monitoring
- centralized logging
- service isolation
- standardized administration

# 5. Real-Life Example

Think about a hotel.

The hotel has:

```text
Security
Electricity
Water
Reception
Housekeeping
Internet
```

These are ongoing services.

If the hotel restarts operations after maintenance, important services need to come back in the correct way.

A Linux server works similarly.

```text
Linux Server
│
├── Network
├── SSH
├── Web Server
├── Database
└── Application
```

Each service has a role.



and:

```bash

```

Understanding these commands is essential.

# 7. What is a Daemon?

A daemon is a background process that typically provides a service.

Examples:

```text
sshd
cron
nginx
dockerd
systemd-journald
```

Many daemon names end with:

```text
d
```

For example:

```text
sshd
dockerd
systemd-journald
```

However, not every daemon necessarily follows this naming convention.

---

# 8. What is systemd?

`systemd` is the system and service manager used by many modern Linux distributions.

It is responsible for tasks such as:

```text
System boot
Service management
Process supervision
Dependency management
Logging integration
Mount management
Timers
```

Instead of manually managing every process, administrators can use:

```bash
systemctl
```

---

# 9. PID 1

On a typical system using systemd, `systemd` runs as:

```text
PID 1
```

Check:

```bash
ps -p 1 -f
```

Example:

```text
UID        PID  PPID  CMD
root         1     0  /sbin/init
```

On systemd systems, `/sbin/init` may be a symlink or entry leading to systemd.

Check:

```bash
readlink -f /sbin/init
```

You may see:

```text
/usr/lib/systemd/systemd
```

PID 1 has a very important role in the boot process and process supervision.

---

# 10. systemd Architecture

A simplified view:

```text
                    Linux Kernel
                         |
                         ↓
                      systemd
                       PID 1
                         |
        +----------------+----------------+
        |                |                |
       SSH              Nginx          Database
     Service           Service          Service
        |                |                |
     sshd             nginx            mysqld
```

`systemd` manages these services using **unit files**.

# 11. What is systemctl?

`systemctl` is the primary command used to communicate with systemd.

Basic structure:

```bash
systemctl <action> <unit>
```

Examples:

```bash
systemctl status nginx
systemctl start nginx
systemctl stop nginx
systemctl restart nginx
```

For administrative actions, you may need:

```bash
sudo
```

Example:

```bash
sudo systemctl restart nginx
```

# 17. Restart a Service

Restart:

```bash
sudo systemctl restart nginx
```

This stops and starts the service.

Use restart when:

- configuration changes require a restart
- the service is stuck
- an approved operational procedure requires it

Always understand the impact in production.

---

# 18. Reload a Service

Some services support configuration reloads without completely stopping the service.

Example:

```bash
sudo systemctl reload nginx
```

A reload may allow the service to:

```text
Read new configuration
Keep existing connections where supported
Avoid a full process restart
```

Not every service supports reload.

---

## Restart vs Reload

| Restart | Reload |
|---|---|
| Stops and starts service | Reloads configuration |
| May interrupt connections | Often less disruptive |
| New process may be created | Process may remain running |
| More disruptive | Usually less disruptive |

Always check the application's documentation and service behavior.

# 19. Enable a Service

`enable` means:

> Configure the service to start automatically during the appropriate boot target.

Example:

```bash
sudo systemctl enable nginx
```

Important:

```text
enable ≠ start
```

It configures future boot behavior.

---

# 20. Disable a Service

Disable automatic startup:

```bash
sudo systemctl disable nginx
```

This does not necessarily stop a currently running service.

To stop it now:

```bash
sudo systemctl stop nginx
```

---

# 21. Enable and Start a Service

You can do both:

```bash
sudo systemctl enable --now nginx
```

This means:

```text
Enable for future boots
        +
Start now
```

# 24. Mask and Unmask a Service

Masking prevents a service from being started normally.

Mask:

```bash
sudo systemctl mask nginx
```

After masking, attempts to start it will generally fail.

Unmask:

```bash
sudo systemctl unmask nginx
```

### Production warning

Do not mask services casually.

Masking is stronger than disabling.

```text
disable
   ↓
Does not automatically start

mask
   ↓
Prevents normal manual/automatic starts
```

# 36. systemd Service Unit

systemd uses **unit files** to describe services.

A service unit normally ends with:

```text
.service
```

Example:

```text
nginx.service
```

When using `systemctl`, you can often omit `.service`:

```bash
systemctl status nginx
```

is equivalent to:

```bash
systemctl status nginx.service
```

---

# 37. What is a Unit?

A unit is a resource managed by systemd.

Examples:

```text
Service
Socket
Timer
Mount
Target
Path
Device
```

Examples:

```text
nginx.service
backup.timer
multi-user.target
```

---

# 38. Types of systemd Units

| Unit | Purpose |
|---|---|
| `.service` | Services |
| `.socket` | Sockets |
| `.target` | Groups/synchronization points |
| `.timer` | Scheduled tasks |
| `.mount` | Filesystem mounts |
| `.path` | Path-based activation |
| `.automount` | Automounts |
| `.device` | Devices |
| `.swap` | Swap devices/files |

For this module, the most important are:

```text
.service
.target
.timer
```

# 39. Service Unit File Structure

A service file commonly contains:

```ini
[Unit]
Description=My Application

[Service]
ExecStart=/opt/myapp/start.sh
Restart=on-failure
User=myapp

[Install]
WantedBy=multi-user.target
```

There are three important sections:

```text
[Unit]
[Service]
[Install]
```

---

# 40. Unit Section

Example:

```ini
[Unit]
Description=My Application Service
After=network.target
```

`Description` explains the purpose.

`After` defines ordering.

For example:

```text
Network
   ↓
Application
```

---

# 41. Service Section

Example:

```ini
[Service]
User=myapp
ExecStart=/opt/myapp/start.sh
Restart=on-failure
```

This section controls how the service runs.

---

# 42. Install Section

Example:

```ini
[Install]
WantedBy=multi-user.target
```

This determines how the service can be enabled.

A common command is:

```bash
sudo systemctl enable myapp
```

---

# 43. Common systemd Options

| Option | Purpose |
|---|---|
| `Description` | Service description |
| `After` | Ordering |
| `Before` | Reverse ordering |
| `Requires` | Required dependency |
| `Wants` | Preferred dependency |
| `User` | User running service |
| `Group` | Group running service |
| `ExecStart` | Start command |
| `ExecStop` | Stop command |
| `ExecReload` | Reload command |
| `Restart` | Restart behavior |
| `RestartSec` | Delay before restart |
| `Environment` | Environment variables |
| `WorkingDirectory` | Working directory |
| `WantedBy` | Target used for enablement |

---

# 44. After vs Requires

These are frequently confused.

### `After=`

Defines ordering.

Example:

```ini
After=network.target
```

Meaning:

> Start this service after the specified unit has been started as far as systemd's ordering rules require.

It does not by itself create a dependency.

---

### `Requires=`

Defines a dependency.

Example:

```ini
Requires=database.service
```

Meaning the service requires that unit.

Simple way to remember:

```text
After
 ↓
Order

Requires
 ↓
Dependency
```

---

# 45. ExecStart

Defines the command systemd should run.

Example:

```ini
ExecStart=/opt/myapp/start.sh
```

Another:

```ini
ExecStart=/usr/bin/java -jar /opt/myapp/app.jar
```

Use an appropriate absolute path.

---

# 46. ExecStop

Defines how systemd should stop the service.

Example:

```ini
ExecStop=/opt/myapp/stop.sh
```

Not every service needs an explicit `ExecStop`; systemd can manage many processes through its normal process control.

---

# 47. Restart Policy

Example:

```ini
Restart=on-failure
```

This tells systemd to restart the service when it fails.

Other common values include:

```text
no
on-success
on-failure
on-abnormal
on-abort
always
```

For example:

```ini
Restart=on-failure
RestartSec=5
```

means:

```text
Service fails
    ↓
Wait 5 seconds
    ↓
Try restarting
```

### Important

Automatic restart is not a replacement for finding the root cause.

A service that crashes repeatedly may enter a restart loop.

---

# 48. Environment Variables in Services

A service may require environment variables such as:

```text
APP_ENV=production
PORT=8080
DATABASE_HOST=db.internal
```

One simple approach:

```ini
[Service]
Environment="APP_ENV=production"
Environment="PORT=8080"
```

Then:

```ini
ExecStart=/opt/myapp/start.sh
```

Another common pattern is an environment file:

```ini
EnvironmentFile=/etc/myapp/myapp.env
```

Example:

```text
APP_ENV=production
PORT=8080
```

Be careful with secrets.

Do not casually store:

```text
PASSWORD=...
API_KEY=...
TOKEN=...
```

in world-readable files.

Follow your organization's secret-management standards.

# 49. Creating a Custom Service

Let's create a simple application service.

We will create:

```text
myapp.service
```

Our application will run a shell script.

Architecture:

```text
systemd
   |
   ↓
myapp.service
   |
   ↓
start.sh
   |
   ↓
Application
```

---

# 50. Create Application User

For a real service, running as a dedicated non-root user is generally safer.

Create:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin myapp
```

Check:

```bash
id myapp
```

This creates a system account intended for the application.

---

# 51. Create Application Directory

```bash
sudo mkdir -p /opt/myapp
```

Create script:

```bash
sudo nano /opt/myapp/start.sh
```

Add:

```bash
#!/bin/bash

while true
do
    echo "$(date) - My application is running"
    sleep 10
done
```

Make executable:

```bash
sudo chmod +x /opt/myapp/start.sh
```

---

# 52. Create systemd Service File

Create:

```bash
sudo nano /etc/systemd/system/myapp.service
```

Add:

```ini
[Unit]
Description=My Sample Application
After=network.target

[Service]
Type=simple
User=myapp
ExecStart=/opt/myapp/start.sh
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

---

# 53. Understand the Service File

### Description

```ini
Description=My Sample Application
```

Human-readable description.

### After

```ini
After=network.target
```

Defines startup ordering.

### User

```ini
User=myapp
```

Runs the service as the dedicated application user.

### ExecStart

```ini
ExecStart=/opt/myapp/start.sh
```

Command used to start the application.

### Restart

```ini
Restart=on-failure
```

Restart after failure.

### RestartSec

```ini
RestartSec=5
```

Wait five seconds before restarting.

### WantedBy

```ini
WantedBy=multi-user.target
```

Allows the service to be enabled for normal multi-user boot.

---

# 54. Reloading systemd Configuration

Whenever you create or modify a unit file, tell systemd to reload its configuration:

```bash
sudo systemctl daemon-reload
```

Important:

```text
Editing service file
       ↓
daemon-reload
       ↓
systemd reads new configuration
```

`daemon-reload` does not automatically restart your service.

# 62. Service Dependencies

Production applications often depend on other components.

Example:

```text
Application
    |
    +---- Database
    |
    +---- Network
    |
    +---- Storage
```

If the database is unavailable:

```text
Application
     ↓
Database connection fails
     ↓
Application may fail
```

systemd supports dependencies and ordering.

# 64. Boot Process and Services

A simplified boot process:

```text
BIOS/UEFI
   ↓
Bootloader
   ↓
Linux Kernel
   ↓
systemd (PID 1)
   ↓
Targets
   ↓
Services
   ↓
Login / Applications
```

systemd starts required services according to dependencies and boot targets.

# 65. Targets

A target groups units together and represents a system state.

Common targets include:

```text
multi-user.target
graphical.target
rescue.target
emergency.target
```

For server environments, `multi-user.target` is especially important.

---

# 66. `systemctl get-default`

Check the default target:

```bash
systemctl get-default
```

Example:

```text
multi-user.target
```

This tells you which target systemd normally enters during boot.

# 67. `systemctl set-default`

Changing the default target affects how the system boots.

Example:

```bash
sudo systemctl set-default multi-user.target
```

### Production warning

Do not change the default target on a production server unless you understand the impact and have authorization.

# 91. Production Safety Rules

## Rule 1 — Status first

Before restarting:

```bash
systemctl status service
```

---

## Rule 2 — Read logs

Use:

```bash
journalctl -u service -n 100
```

---

## Rule 3 — Do not blindly restart production services

A restart can:

```text
Disconnect users
Terminate connections
Interrupt transactions
Cause downtime
Trigger failover
```

Follow the approved operational procedure.

---

## Rule 4 — Understand restart vs reload

Use the least disruptive approved action.

```text
reload
   ↓
Usually less disruptive

restart
   ↓
More disruptive
```

---

## Rule 5 — Check dependencies

Before restarting an application:

```text
Database
Network
Storage
External services
Certificates
```

may matter.

---

## Rule 6 — Never edit production unit files casually

A systemd unit can control a critical production application.

Follow:

```text
Change
   ↓
Review
   ↓
Approval
   ↓
Implementation
   ↓
Verification
```

# 🎯 Final Mindset

When an Application Support ticket says:

> "Application is down."

Do not immediately restart the service.

Think:

```text
Application Down
      ↓
Is service running?
      ↓
systemctl status
      ↓
What do the logs say?
      ↓
journalctl
      ↓
Is the process running?
      ↓
Is the expected port listening?
      ↓
Are dependencies available?
      ↓
Is configuration valid?
      ↓
What caused the failure?
      ↓
What is the approved action?
      ↓
Restart / Reload / Fix
      ↓
Verify
      ↓
Document
```

The important lesson is:

> **`systemctl restart` is an action, not a troubleshooting strategy.**

A professional Application Support Engineer first understands **why the service failed**, takes the safest approved action, verifies recovery, and documents the result.
