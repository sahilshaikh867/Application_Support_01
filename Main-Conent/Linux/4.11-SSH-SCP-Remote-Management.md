# 1. Introduction

Imagine your company has a production application running on a Linux server in AWS.

You are sitting at home.

The server is in a cloud data center.

A customer reports:

> "The application is not working."

How will you access the server?

You cannot physically go to the server.

Instead, you connect remotely using:

```text
SSH
```

After connecting, you might execute commands such as:

```bash
systemctl status nginx
```

```bash
tail -f /var/log/application.log
```

```bash
df -h
```

```bash
free -m
```

```bash
ps aux
```

This is why SSH is extremely important in Linux administration and Application Support.

---

# 2. What is SSH?

**SSH** stands for:

> **Secure Shell**

SSH is a network protocol used to securely connect to and manage a remote computer.

Example:

```bash
ssh sahil@192.168.1.100
```

Here:

```text
ssh       → SSH client command
sahil     → remote username
192.168.1.100 → remote server IP
```

After successful authentication, you get a shell on the remote server.

```text
Your Computer
     |
     | SSH
     ↓
Remote Linux Server
```

---

# 3. Why Do We Need SSH?

SSH allows us to:

- Connect to remote Linux servers
- Execute commands
- Manage applications
- Check logs
- Restart services
- Troubleshoot problems
- Transfer files
- Configure servers
- Deploy applications
- Monitor systems
- Perform administrative tasks

```text
Production Server
IP: 10.10.20.50
```

You receive an incident:

```text
INC001245

Application is not responding.
```

You connect:

```bash
ssh supportuser@10.10.20.50
```

Then investigate:

```bash
systemctl status myapp
```

Check logs:

```bash
journalctl -u myapp -n 100
```

Check disk:

```bash
df -h
```

Check memory:

```bash
free -h
```

Check ports:

```bash
ss -lntp
```

This is a typical Application Support workflow.

# 5. SSH Client and SSH Server

SSH communication normally involves two sides.

## SSH Client

The machine from which you connect.

Example:

```text
Your Laptop
```

You execute:

```bash
ssh user@server
```

---

## SSH Server

The remote machine accepting SSH connections.

The SSH server normally runs:

```text
sshd
```

`sshd` means:

> SSH daemon

---

## Example

```text
Laptop
SSH Client
     |
     | TCP 22
     ↓
Linux Server
SSH Server (sshd)
```

---

# 6. SSH Architecture

Basic architecture:

```text
+-----------------------+
|      Your Laptop      |
|                       |
|     SSH Client        |
+-----------+-----------+
            |
            |
            | Secure SSH Connection
            |
            ↓
+-----------------------+
|    Remote Server      |
|                       |
|       sshd            |
|   SSH Server          |
+-----------------------+
```

Authentication happens before access is granted.

```text
Client
  |
  | Connection
  ↓
SSH Server
  |
  | Authentication
  ↓
Password / Key Verification
  |
  ↓
Shell Access
```

# 7. SSH Port

By default, SSH uses:

```text
TCP Port 22
```

Example:

```text
Server IP: 192.168.1.100
Port: 22
```

So conceptually:

```text
192.168.1.100:22
```

SSH can also be configured to use another port.

For example:

```text
2222
```

But changing the port alone is **not a complete security strategy**.

---

# 8. Checking SSH Service

On a Linux server using systemd:

```bash
systemctl status ssh
```

Some distributions use:

```bash
systemctl status sshd
```

Start:

```bash
sudo systemctl start ssh
```

or:

```bash
sudo systemctl start sshd
```

Restart:

```bash
sudo systemctl restart ssh
```

Enable at boot:

```bash
sudo systemctl enable ssh
```

Check whether it is listening:

```bash
ss -lntp | grep ':22'
```

Example:

```text
LISTEN 0 128 0.0.0.0:22
```

This indicates that something is listening on port 22.

# 9. Basic SSH Command

The basic syntax is:

```bash
ssh username@hostname
```

or:

```bash
ssh username@IP_ADDRESS
```

Example:

```bash
ssh ubuntu@192.168.1.100
```

Another example:

```bash
ssh supportuser@10.10.20.50
```

# 10. Connecting to a Remote Server

Suppose:

```text
Username: supportuser
Server IP: 192.168.1.100
```

Run:

```bash
ssh supportuser@192.168.1.100
```

You may see:

```text
The authenticity of host '192.168.1.100' can't be established.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

For a server you have verified and intend to trust, you can type:

```text
yes
```

Then SSH may ask for:

```text
supportuser@192.168.1.100's password:
```

Enter the password.

---

# 11. Custom SSH Port

If SSH is running on a different port:

```bash
ssh -p 2222 user@server
```

Example:

```bash
ssh -p 2222 supportuser@10.10.20.50
```

Here:

```text
-p → port
2222 → SSH port
```

# 12. Password Authentication

The simplest SSH authentication method is password authentication.

Example:

```bash
ssh user@server
```

Then:

```text
Password:
```

Enter the user's password.

However, production environments often prefer SSH key authentication because it can provide stronger security and better automation when configured correctly.

---

# 13. SSH Keys

SSH supports public-key authentication.

SSH keys normally come as a pair:

```text
Private Key
+
Public Key
```

Example:

```text
Private Key:
~/.ssh/id_ed25519

Public Key:
~/.ssh/id_ed25519.pub
```

---

# 14. Public Key and Private Key

This concept is extremely important.

## Private Key

The private key should remain secret.

```text
DO NOT SHARE
```

Example:

```text
~/.ssh/id_ed25519
```

---

## Public Key

The public key can be placed on the server.

Example:

```text
~/.ssh/id_ed25519.pub
```

---

## Simple Diagram

```text
Your Computer
---------------------

Private Key
     |
     | Authentication
     ↓
SSH Client
     |
     ↓
Remote Server
     |
     ↓
Public Key
```

The private key stays with the client.

The server stores the authorized public key.

---

# 15. Generating SSH Keys

Modern OpenSSH commonly supports Ed25519 keys.

Generate one:

```bash
ssh-keygen -t ed25519
```

You may see:

```text
Enter file in which to save the key:
```

Press Enter to use the default location.

Then you may be asked for a passphrase.

A passphrase is recommended for protecting the private key.

---

## Generated Files

Typically:

```text
~/.ssh/id_ed25519
```

Private key.

And:

```text
~/.ssh/id_ed25519.pub
```

Public key.

---

# 16. The ~/.ssh Directory

SSH-related user configuration normally exists under:

```bash
~/.ssh/
```

Example:

```text
~/.ssh/
├── id_ed25519
├── id_ed25519.pub
├── authorized_keys
├── known_hosts
└── config
```

Let's understand them.

| File | Purpose |
|---|---|
| `id_ed25519` | Private key |
| `id_ed25519.pub` | Public key |
| `authorized_keys` | Public keys allowed to log in |
| `known_hosts` | Host keys previously trusted |
| `config` | Client-side SSH configuration |

---

# 17. authorized_keys

On the remote server, authorized public keys are commonly stored in:

```bash
~/.ssh/authorized_keys
```

Example:

```text
Server
└── /home/sahil/.ssh/authorized_keys
```

It can contain public keys that are allowed to authenticate as that user.

Conceptually:

```text
Your Laptop
Private Key
     |
     ↓
SSH Authentication
     |
     ↓
Server
authorized_keys
     |
     ↓
Access granted
```

---

# 18. known_hosts

Your SSH client maintains information about remote hosts it has connected to.

Usually:

```bash
~/.ssh/known_hosts
```

This helps SSH detect unexpected host key changes.

For example, you previously connected to:

```text
server.example.com
```

If the server's host key suddenly changes, SSH may warn you.

This can happen for legitimate reasons, such as a server rebuild, but it can also indicate a security problem.

**Do not blindly delete or ignore host-key warnings in production.**

---

# 19. Password vs SSH Key Authentication

| Feature | Password | SSH Key |
|---|---|---|
| Easy for beginners | Yes | Moderate |
| Automation | Poor | Excellent |
| Secret shared with server | Password verification | Private key stays client-side |
| Brute-force exposure | Higher | Can be reduced significantly |
| Production use | Sometimes | Very common |
| CI/CD | Not ideal | Common |

# 20. Copying SSH Keys to a Server

On many Linux systems, you can use:

```bash
ssh-copy-id username@server
```

Example:

```bash
ssh-copy-id supportuser@192.168.1.100
```

This normally installs your public key into the remote user's:

```text
~/.ssh/authorized_keys
```

After that, you can authenticate using your private key.

---

## Manual Method

You can also copy the public key:

```bash
cat ~/.ssh/id_ed25519.pub
```

Copy the output.

Then add it to:

```bash
~/.ssh/authorized_keys
```

on the server.

Be careful with permissions.

Typical secure permissions include:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

---

# 21. SSH Config File

Instead of repeatedly typing:

```bash
ssh supportuser@192.168.1.100
```

you can create:

```bash
~/.ssh/config
```

Example:

```text
Host production
    HostName 192.168.1.100
    User supportuser
    Port 22
```

Then simply run:

```bash
ssh production
```

---

## Another Example

```text
Host app-server
    HostName 10.10.20.50
    User appuser
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```

Now:

```bash
ssh app-server
```

---

# 22. ssh-agent and ssh-add

If your private key is protected with a passphrase, repeatedly entering the passphrase can be inconvenient.

`ssh-agent` can hold private keys in memory for authentication.

Start an agent:

```bash
eval "$(ssh-agent -s)"
```

Add your key:

```bash
ssh-add ~/.ssh/id_ed25519
```

List loaded keys:

```bash
ssh-add -l
```

Remove all loaded keys:

```bash
ssh-add -D
```

Use this carefully on shared or untrusted systems.

# 23. Executing Commands Remotely

SSH does not require an interactive shell.

You can execute a command directly:

```bash
ssh user@server "hostname"
```

Example:

```bash
ssh supportuser@10.10.20.50 "uptime"
```

Another example:

```bash
ssh supportuser@10.10.20.50 "df -h"
```

Another:

```bash
ssh supportuser@10.10.20.50 "systemctl status nginx"
```

This is extremely useful for automation.

---

## Multiple Commands

Example:

```bash
ssh supportuser@10.10.20.50 "hostname; uptime; df -h"
```

For more complex commands, quoting becomes important.

# 24. SCP

**SCP** stands for:

> Secure Copy Protocol

It allows files to be copied between systems over SSH.

Basic syntax:

```bash
scp source destination
```

---

# 25. Uploading Files

Suppose you have:

```text
application.log
```

on your local computer.

Upload it to:

```text
/home/supportuser/logs/
```

Command:

```bash
scp application.log supportuser@192.168.1.100:/home/supportuser/logs/
```

Flow:

```text
Local Computer
      |
      | SCP
      ↓
Remote Server
```

---

# 26. Downloading Files

Suppose the remote server has:

```text
/var/log/application.log
```

Download it:

```bash
scp supportuser@192.168.1.100:/var/log/application.log .
```

`.` means:

```text
Current directory
```

---

## Download to Specific Directory

```bash
scp supportuser@192.168.1.100:/var/log/application.log ~/Downloads/
```

---

# 27. Copying Directories

Use:

```bash
scp -r directory user@server:/destination/
```

Example:

```bash
scp -r logs supportuser@192.168.1.100:/home/supportuser/
```

Here:

```text
-r → recursive
```

This copies the directory and its contents.

---

# 28. Rsync

`rsync` is another important tool for transferring and synchronizing files.

Example:

```bash
rsync -av logs/ supportuser@192.168.1.100:/home/supportuser/logs/
```

Common options:

```text
-a → archive
-v → verbose
```

For larger directories or repeated synchronization, `rsync` is often more efficient than copying everything repeatedly.

---

## Example

```bash
rsync -av ./application/ supportuser@server:/opt/application/
```

Be very careful with options such as:

```text
--delete
```

because they can remove destination files that are not present in the source.

---

# 29. SFTP

**SFTP** stands for:

> SSH File Transfer Protocol

It provides interactive file transfer over SSH.

Connect:

```bash
sftp user@server
```

Inside SFTP:

```bash
ls
```

List remote files.

```bash
pwd
```

Show remote directory.

```bash
lpwd
```

Show local directory.

```bash
get file.txt
```

Download a file.

```bash
put file.txt
```

Upload a file.

```bash
exit
```

Exit SFTP.

# 30. SSH Server Configuration

The SSH server configuration is commonly located at:

```text
/etc/ssh/sshd_config
```

You can inspect it:

```bash
sudo less /etc/ssh/sshd_config
```

Common configuration areas include:

```text
Port
PermitRootLogin
PasswordAuthentication
PubkeyAuthentication
AllowUsers
AllowGroups
```

**Never change production SSH configuration casually.**

A wrong SSH configuration can lock administrators out of the server.

---

# 31. sshd

`sshd` is the SSH server daemon.

Check:

```bash
systemctl status sshd
```

or on some distributions:

```bash
systemctl status ssh
```

Find the process:

```bash
ps aux | grep sshd
```

Check listening port:

```bash
ss -lntp | grep ssh
```

# 32. SSH Logs

SSH problems often require checking logs.

On systemd systems:

```bash
journalctl -u ssh
```

or:

```bash
journalctl -u sshd
```

Follow logs:

```bash
journalctl -u sshd -f
```

On some Linux distributions, authentication logs can also be found in files such as:

```text
/var/log/auth.log
```

or:

```text
/var/log/secure
```

Distribution-specific locations vary.

# 33. Firewall and SSH

Even if SSH is running, a firewall can block access.

For example:

```text
Client
  |
  | TCP 22
  ↓
Firewall
  X
SSH Server
```

Common firewall tools include:

```text
ufw
firewalld
nftables
iptables
```

Check listening ports:

```bash
ss -lntp
```

For UFW:

```bash
sudo ufw status
```

For firewalld:

```bash
sudo firewall-cmd --list-all
```

Cloud environments may also have network controls outside the Linux server, such as cloud security groups or network ACLs.

# 34. SSH Troubleshooting

SSH troubleshooting is an important Application Support skill.

Use a structured approach.

---

## Problem 1: Connection Refused

Error:

```text
ssh: connect to host server port 22: Connection refused
```

Possible reasons:

- SSH service is not running
- Wrong port
- Server is reachable but nothing is listening
- Firewall is rejecting the connection

Check server:

```bash
systemctl status ssh
```

Check port:

```bash
ss -lntp | grep ':22'
```

---

# Problem 2: Connection Timed Out

Example:

```text
Connection timed out
```

Possible reasons:

- Network problem
- Firewall
- Security group
- Server unreachable
- Wrong IP
- Routing problem

Test:

```bash
ping server
```

Then:

```bash
nc -vz server 22
```

or:

```bash
telnet server 22
```

where telnet is available and appropriate.

---

# Problem 3: Permission Denied

Example:

```text
Permission denied (publickey,password)
```

Possible causes:

- Wrong username
- Wrong password
- Wrong private key
- Public key not installed
- Incorrect `authorized_keys`
- Incorrect permissions
- SSH configuration problem

Run SSH in verbose mode:

```bash
ssh -v user@server
```

For more detail:

```bash
ssh -vvv user@server
```

---

# Problem 4: Wrong Username

Suppose the server expects:

```text
ubuntu
```

but you try:

```bash
ssh root@server
```

Authentication may fail.

Try the correct account:

```bash
ssh ubuntu@server
```

---

# Problem 5: Wrong SSH Port

Maybe SSH runs on:

```text
2222
```

but you try:

```bash
ssh user@server
```

Use:

```bash
ssh -p 2222 user@server
```

---

# Problem 6: SSH Service Down

Check:

```bash
systemctl status sshd
```

If appropriate:

```bash
sudo systemctl start sshd
```

But remember:

> Do not restart production SSH services blindly.

First understand the environment and impact.

---

# Problem 7: Host Key Changed

You may see a warning similar to:

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

Possible reasons:

- Server was rebuilt
- Host key was intentionally changed
- DNS/IP now points to another server
- Potential security issue

Do not blindly remove the entry.

First verify with your infrastructure/team that the server identity really changed.

---

# Problem 8: Public Key Authentication Failure

Check:

```bash
ls -la ~/.ssh/
```

Verify:

```text
id_ed25519
id_ed25519.pub
```

Check remote:

```bash
ls -la ~/.ssh/
```

Verify:

```text
authorized_keys
```

Check permissions:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Then investigate SSH logs.

---

# 35. SSH Security Best Practices

SSH provides secure remote access, but it still needs proper configuration.

## 1. Protect Private Keys

Never share:

```text
id_ed25519
```

Do not upload private keys to:

- GitHub
- Slack
- Email
- Public websites
- Tickets

---

## 2. Use SSH Keys

Where appropriate, use strong key-based authentication instead of relying only on passwords.

---

## 3. Use Passphrases

Protect private keys with passphrases.

---

## 4. Disable Direct Root Login Where Appropriate

Depending on your environment:

```text
PermitRootLogin no
```

should be considered as part of a broader access-control strategy.

Do not make changes without confirming how administrative access is designed.

---

## 5. Use Least Privilege

Do not give every user:

```text
root
```

access.

Use:

```bash
sudo
```

with appropriate permissions.

---

## 6. Restrict SSH Access

Where appropriate, use:

```text
AllowUsers
```

or:

```text
AllowGroups
```

---

## 7. Use Firewalls

Only expose SSH where it is required.

---

## 8. Monitor Authentication

Regularly review:

```text
SSH logs
```

for suspicious login attempts.

---

## 9. Avoid Secrets in Commands

Avoid commands such as:

```bash
ssh user@server "command --password=mysecret"
```

because command arguments can sometimes become visible through process listings or logs.

Use safer secret-management approaches.

---

# 36. Bastion / Jump Server

In enterprise environments, you may not be allowed to connect directly to production servers.

Instead:

```text
Your Laptop
     |
     ↓
Bastion / Jump Server
     |
     ↓
Production Server
```

A bastion host is a controlled entry point.

Example:

```text
Laptop
   |
   | SSH
   ↓
Bastion
10.10.10.10
   |
   | SSH
   ↓
Production
10.10.20.50
```

Modern OpenSSH also supports jump-host functionality with:

```bash
ssh -J bastionuser@bastion targetuser@production
```

Example:

```bash
ssh -J support@10.10.10.10 appuser@10.10.20.50
```

This can be useful when the production server is reachable only through the bastion.

# 37. Application Support Production Scenario

Imagine an e-commerce application.

Architecture:

```text
Users
  |
  ↓
Load Balancer
  |
  ↓
Application Servers
  |
  ↓
Database
```

One application server becomes unhealthy.

Monitoring generates:

```text
ALERT

Application server app-03
Health check failed.
```

Application Support engineer connects:

```bash
ssh supportuser@app-03
```

Check server:

```bash
hostname
```

Check CPU:

```bash
top
```

Check memory:

```bash
free -h
```

Check disk:

```bash
df -h
```

Check application process:

```bash
ps aux | grep myapp
```

Check service:

```bash
systemctl status myapp
```

Check logs:

```bash
journalctl -u myapp -n 100
```

Check port:

```bash
ss -lntp
```

Suppose the application failed because the disk is full.

Check:

```bash
du -sh /var/log/*
```

You identify a large log file.

You follow your organization's approved procedure for log cleanup/rotation.

Then verify:

```bash
df -h
```

Restart the service only if approved:

```bash
sudo systemctl restart myapp
```

Verify:

```bash
systemctl status myapp
```

Finally, confirm the application health check.

This is how SSH becomes part of a complete Application Support workflow.

# 41. Troubleshooting Lab

Students should intentionally investigate the following scenarios.

## Scenario 1

```text
Connection refused
```

Questions:

1. Is SSH service running?
2. Is port 22 listening?
3. Is the correct port being used?

---

## Scenario 2

```text
Connection timed out
```

Questions:

1. Is the server reachable?
2. Is a firewall blocking the connection?
3. Is the cloud security rule correct?
4. Is routing correct?

---

## Scenario 3

```text
Permission denied
```

Questions:

1. Is username correct?
2. Is password correct?
3. Is public key installed?
4. Is private key correct?
5. Are permissions correct?
6. What do SSH logs say?

---

## Scenario 4

```text
REMOTE HOST IDENTIFICATION HAS CHANGED
```

Questions:

1. Was the server rebuilt?
2. Did its host key change?
3. Did the IP/DNS mapping change?
4. Has the change been verified?

# 🎯 Final Mindset

Do not learn SSH only as a command:

```bash
ssh user@server
```

Understand what happens behind it:

```text
Client
   ↓
Network
   ↓
Server IP
   ↓
Port 22
   ↓
Firewall
   ↓
sshd
   ↓
Authentication
   ↓
User
   ↓
Shell
   ↓
Application Support Investigation
```

In a real Application Support job, SSH is not the final goal.

The real goal is:

> **Connect → Investigate → Find the Problem → Fix Safely → Validate → Document**

That is the mindset you should develop while learning Linux.
